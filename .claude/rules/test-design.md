# テスト設計方針

## グランドルール

テストは「本数」ではなく「守れる振る舞いあたりの保守コスト」で最小化します。
原則としてエントリポイント起点で書き、要所のみ下層に落とします。

## なぜエントリポイント起点か

- カバレッジと堅牢性は別物です。実装構造に結合したテストは、リファクタで壊れる割にバグを捕まえません。
- エントリポイント起点のテストは観測可能な振る舞い（契約）に結合するため、同じ労力で守れる範囲が広くなります。
- 同一の振る舞いを層ごとに重複検証せずに済み、1ケースで縦断的に確認できます。

## 層を下げる判断基準

デフォルトは高い層（E2E・結合）に置きます。次の場合のみ単体テストへ落とします。

| 単体テストが向く場面 | 理由 |
| --- | --- |
| 純粋ロジック（正規化・パース・境界計算・アルゴリズム） | 組み合わせが多く、上位層だと事前準備が過大になる |
| 稀な障害時しか到達しない分岐 | 例: 外部API失敗時のエラーラップ。モックで確実に到達させる |
| 障害箇所の特定が難しい複雑モジュール | 上位層は「どこか壊れた」しか示さないため、要所を局所化する |

## エントリポイント起点の弱点と対策

- 遅くなりやすい（DB・外部呼び出しを通すため）。純粋ロジックは高速な単体テストに残します。
- 原因特定が鈍い。1テスト＝1振る舞いを守り、失敗時に何が壊れたか読めるようにします。
- 到達不能な防御コードは、テストではなくコードの過剰防御を疑います。

## 境界値・異常系

- 境界値試験は実装します（許容の下限と、その直下の不許容を対で置きます）。
- 異常系も、エントリポイントから異常入力を渡して到達させます。単独のヘルパーテストには安易に切り出しません。
