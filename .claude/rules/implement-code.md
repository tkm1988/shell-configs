# コード実装時のルール

レビューの観点も兼ねます。

## グランドルール

```text
コードには How
テストコードには What
コミットログには Why
コードコメントには Why not
```

## 非機能要件

### 可読性・保守性

将来のバグを防ぎ、開発スピードを速く保つため、t_wadaが述べるような以下を気をつける。

- コメントに頼らなくても、処理の目的が伝わる変数名やメソッド名をつける
- マジックナンバーを排除する
- 複雑な条件式は分解する
- もう一人が理解できるコードを書く
- 責任の分離（1つのクラスに1つの役割）
- テスト駆動開発（TDD）を活用する
    - BDDのフォーマットGiven-When-Thenを使うのも良い

### セキュリティ

- OWASPや徳丸本で挙げられるようなセキュリティ上の脆弱な実装を設計・実装時に排除すること
